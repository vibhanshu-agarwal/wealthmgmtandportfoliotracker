- **Demo credentials are configured in four places, and the authoritative one is immutable.**
  `.github/workflows/deploy-azure.yml:267-268` hardcodes `demo@wealthtracker.dev` /
  `demo-wealthtracker-2026` as literals (so the demo password is in git history);
  `frontend/.env.local:1-2` repeats them; `login/page.tsx:9-10` consumes them via
  `NEXT_PUBLIC_*`; and the credential the login actually validates against is a bcrypt hash in
  `portfolio-service/src/main/resources/db/migration/V15__Reconcile_Auth_Seed_Users.sql:28`.
  Because Flyway migrations are immutable once applied, changing any config value does **not**
  rotate the password — it only desynchronises the plaintext copies from the stored hash and
  breaks the demo login silently.

  **Resolved as documentation, not as a config move.** An earlier plan here was to add both keys
  to `.env.secrets`, sync them to GitHub, and have `deploy-azure.yml` read
  `${{ secrets.DEMO_PASSWORD }}`. That plan was wrong and has been dropped:

  - The demo password is **public by design**. `deploy-azure.yml` passes it as
    `NEXT_PUBLIC_DEMO_PASSWORD`, and Next.js inlines every `NEXT_PUBLIC_*` var into the client
    bundle — a public static export — so the value already ships in the site's JavaScript and is
    pre-filled into the login form. Treating it as a secret protects nothing.
  - GitHub masks secret values as `***` in workflow logs. Masking a value printed on the website
    would make debugging harder while falsely implying sensitivity.
  - `scripts/sync-secrets.sh` is `gh secret set -f`, which uploads **every** key in the file with
    no per-key exclusion. There is no way to keep a non-secret in `.env.secrets` without it
    becoming a GitHub Actions secret.

  So the literal in `deploy-azure.yml` stays, and `.env.secrets.example` now records
  `DEMO_EMAIL` / `DEMO_PASSWORD` **with their real values**, alongside a comment naming all four
  locations and why each exists. The file is allowlisted in `.gitleaks.toml` precisely so it can
  hold non-secret literals, and traceability from one place is worth more than minimising copies
  — an undocumented copy is the thing that actually causes drift.

  Rotation is still a migration, not a config change: update `user_credentials` in a NEW Flyway
  migration and change all copies in the same PR. Verified in step as of 2026-08-15 —
  `deploy-azure.yml:267-268`, `.env.secrets.example:190-191`, and `frontend/.env.local:1-2` all
  read `demo@wealthtracker.dev` / `demo-wealthtracker-2026`.
