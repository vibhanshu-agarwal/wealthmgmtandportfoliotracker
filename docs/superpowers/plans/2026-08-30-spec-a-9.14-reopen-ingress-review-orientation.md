## Reversal path

A guarded reverse profile `spec-a-9.14-close-ingress` exists and is asserted by the same script in
the opposite ingress direction, so a reopen is reversible by the same bounded mechanism.

onward: disabling the holding validator, **or** rolling back to an R3 artifact whose defaults are
permissive, requires quiescing writes first and keeping them closed until the forward fix deploys.

### Observation — pre-apply single-tracking (non-blocking)

PR #184 also flipped `api_gateway_ingress_enabled`'s default from `false` to `true` and added a
workflow env line that resolves it to `true` for **every** profile except `spec-a-9.14-close-ingress`:

```yaml
TF_VAR_api_gateway_ingress_enabled: ${{ github.event.inputs.change_profile == 'spec-a-9.14-close-ingress' && 'false' || 'true' }}
```

While live ingress is closed, that means any other profile would plan a gateway ingress transition,
which `_evaluate_non_scoped` rejects as `FAIL [ingress-guard]`; and `spec-a-9.14-close-ingress`
fails its own precondition because `before` has no external ingress to close. Evaluating the
reopen-shaped plan against all twelve `KNOWN_PROFILES` confirms this: ten fail `[ingress-guard]`,
`close-ingress` fails `[ingress] before must expose one external ingress block`, and only
`spec-a-9.14-reopen-ingress` passes.

**So `spec-a-9.14-reopen-ingress` is currently the only profile that can pass the plan guards.**

This is fail-closed — it blocks, it never silently mutates — and it is **not an apply blocker**: the
9.14 apply is precisely what clears it. It is recorded because it is a real, bounded operational
constraint. Until 9.14 applies, unrelated Terraform work (a `standard` rollout, a 9.13-style scale
change) is blocked too, and the escape hatches are to apply 9.14 or to revert the variable default
and workflow line. The "Reversal path" section above remains accurate for post-apply reversibility;
this observation covers the pre-apply window it does not describe.
